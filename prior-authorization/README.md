# Prior authorization

An evidence-based policy check on a healthcare prior-authorization request. A request asks: does the evidence on
file meet the coverage policy for this procedure? The service loads the active policy, reads the member's evidence,
checks every rule and answers **Pass**, **Warn** or **Block**, with a report and one stored finding per rule. A Block
is never final on its own: a clinical reviewer upholds or overrides it, so there is no automatic denial.

Built with [tuvl](https://tuvl.io) 2.0 — try it without installing at [try.tuvl.online](https://try.tuvl.online).
All data is synthetic.

## What it demonstrates

- **Determinism.** The verdict is a pure function of the policy version, the evidence and the request. No model is
  called and no clock is read: `evaluate_rules` is plain code, and `classify` is a visible `decide rules` step
  (`blocking > 0` → block, `warnings > 0` → warn, otherwise pass). The offline tests include the same evidence in two
  orders giving the same verdict.
- **Policy as data.** A `PolicyVersion` holds a list of rules (`diagnosis_in`, `has_evidence`, `attr_min`). Publishing a
  version checks the rules first; a policy that fails the check is refused and the last good version stays active.
- **Fail closed.** No active policy, or a failed step, never yields a Pass.
- **Human in the loop, with segregation of duties.** A Block waits for the `clinical_reviewers` group, and the person
  who started the run cannot decide it.
- **Audit trail.** Every evaluation keeps the policy version it used, a report and one finding per rule with the
  evidence row it relied on. The run journal records each step.
- **Privacy.** `member_ref` is a `secure` field, so it never reaches a model.
- **Its own screens.** `ui/index.html` is a small single-page app (no build step) with a screen for each role.

## Spec, tests and the CI gate

The intent lives in [`specs/prior-authorization-check.md`](specs/prior-authorization-check.md). Its `tuvl-example`
blocks are the tests in `tests/`, and all of it runs offline:

```bash
tuvl lint spec && tuvl lint project --strict && tuvl generate code --check && tuvl verify lock && tuvl run tests --strict && tuvl verify spec --strict && tuvl list tasks --strict
```

## Run it

Prerequisites: [tuvl](https://tuvl.dev/getting-started/installation/) 2.0, and PostgreSQL 15+ with a `tuvl_prior_auth`
database. No model key is needed.

```bash
cp .env.example .env                                   # set the Postgres password
TUVL_CORS_ORIGINS=http://localhost:8090 tuvl dev --auto-login --port 8885
python scripts/seed_demo.py --url http://localhost:8885   # demo policy, synthetic evidence, three demo users
cd ui && python -m http.server 8090                    # then open http://localhost:8090/?api=http://localhost:8885
```

The three demo people (password `demo-pass-1`, throwaway data only):

| Person | Role | Can |
|---|---|---|
| `intake@demo.test` | `reviewers` | evaluate requests, read the audit trail |
| `dr.chen@demo.test` | `clinical_reviewers` | decide blocked requests (not her own) |
| `policy@demo.test` | `policy_admins` | publish coverage policies |

Try the scenarios on the Evaluate screen: a request that meets every rule passes, a missing clinical note warns, and
too little therapy or an uncovered diagnosis is held for clinical review.
